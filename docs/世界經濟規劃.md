## 0. 先講結論

1. **外面世界就是「台灣整體經濟」的縮小版**：池子規模是 台灣名目 GDP × φ（φ＝0.04%，等於現在的 100 億，餘額不動）。每天成長照台灣的真實年增率走。
2. **外面世界裡有「單位」，是一棵樹**：第一版先定 7 個大集團／組織（島上科技、海外科技、民生、金融、文化藝術、學校研究、公共機構），館外股票那 11 家掛在科技集團底下；公司、子公司以後再接（資料用 `parent`，不寫死兩層）。**文化部獨立**，是劇情單位，不放在任何集團底下。池子＝公共池＋所有單位現金，**總和就是現在的池子**，只是分帳。
3. **NPC 先隸屬一個集團（之後再細分到公司），有職位和薪水**；預算先在集團層級算總額再分下去。第一階段薪水只是「預算」：NPC 來館花的錢，改從所屬單位出（現在是從公共池出）；第二階段 NPC 才有自己的錢包。
4. **單位好壞連動景氣和股價**，影響薪水倍率，進而影響 NPC 的預算和來館人數。有下限，不會讓館內人流一夜消失。
5. **資料拆成小份**（世界一份、每個單位一份、每位 NPC 一份），換日和發薪由伺服器每天自己跑，併進 05:05 那次排程；館友按鈕不碰這些文件。
6. **每種要定期更新的資料都配一支腳本**（第 7 節），排程和 AI 不手改 JSON。
7. **分 6 步做**，每步一個 PR，每步都有守恆檢查。

## 1. 外面世界的量級

### 1.1 現在

| 項目 | 現在 | 出處 |
| --- | --- | --- |
| 池子起始 | 100 億 | `NUM.casino.world.start` |
| 每天成長（憑空，記 `worldGrow`） | 500 萬 ×（1＋20%×景氣） | `growBase`、`growExtPct` |
| 吃緊線 | 低於起始的 10% | `lowPct` |
| 館從外面世界拿錢的上限 | 散客門票 ≤ 每天成長的 10%、NPC 來館 ≤ 20% | `crowd.dayCap`、`npcSpend.extPct`、`econ:check` |
| 外部景氣 | 最新一季年增率 − 近四季平均，÷3 夾 ±1 | `content/economy.json`、`casGdpExt` |

NPC 來館實際花的錢（`npc_spend.test.cjs sim`）：每天約 13 萬，是每天成長 500 萬的 2.6%。就是說外面世界對館來說很大，館只碰到一小塊。

### 1.2 建議（接幣值規劃 8.3）

- 池子規模固定：台灣名目 GDP（一年約 25 兆，**要以主計總處公布為準，實作前由排程去查**）× φ。φ 用現在的池子反推，約 0.04%。
- 每天成長 ＝ 池子 × 年增率 ÷ 365 ×（1＋20%×景氣）。年增率用 `content/economy.json` 近四季平均（13.9%）；100 億 × 13.9% ÷ 365 ≈ 380 萬，跟現在的 500 萬同一個量級。
- 資料欄位：`content/economy.json` 的 `gdp` 加 `nominalYear`、`nominalAsOf`、`source`，跟 `yoy` 一樣，只在主計總處有新公布時由每日排程更新。
- 池子規模不隨 GDP 重新調（要改 φ 就寫決定）。**所有館內上限都按「φ 之後的池子」算，不用改。**

### 1.3 單位出現後，成長怎麼分

外面世界的「憑空」仍然只有一個來源：每天成長（`worldGrow`）。有了單位之後，成長不再全進公共池，**按單位的權重分給各單位**：

```text
當天成長 G ＝ 池子規模 × 年增率 ÷ 365 ×（1＋20%×景氣）
單位 i 分到 G × w_i × (1 ＋ 行業係數_i × 景氣)，再正規化到總和 ＝ G
```

- `w_i`：這個單位占外面世界的比例（名單裡寫，總和 ≤ 90%，剩下的留公共池）。
- 行業係數：景氣好時「景氣敏感」的行業（科技、營建）多分一點，「防禦」的行業（食品、公家機關）少變動。係數小（±0.3 以內）。
- **正規化**保證總成長不變，所以 `econ:check`、對帳差不會被這個動到。

### 2.2 資料結構：允許任意深度

單一格式，**用 `parent` 指向上一層**，不寫死兩層。第一版只有集團（`parent` 為 null），之後可以加公司、子公司。

```json
{
  "id": "g-island",
  "name": "島上科技集團",
  "kind": "group",
  "parent": null,
  "sector": "tech",
  "share": 0.12,
  "staff": 18000,
  "stocks": ["islandforge", "handbrain", "bigassembly", "trianglepower", "linetower"],
  "story": false
}
```

之後接公司：

```json
{ "id": "c-islandforge", "name": "島上鑄晶坊", "kind": "firm", "parent": "g-island", "sector": "tech", "share": 0.03, "stocks": ["islandforge"], "staff": 4000 }
```

| 欄位 | 意思 |
| --- | --- |
| `parent` | 上一層單位的 id；頂層是 `null`。檢查：不能繞圈、不能指向不存在的 id |
| `kind` | `group`（集團／組織）、`firm`（公司）、`org`（機構）、`story`（劇情單位，見 2.4） |
| `sector` | 行業：tech、daily、finance、arts、school、public…；決定景氣係數 |
| `share` | 占外面世界的比例。**同一個 `parent` 底下的子單位 `share` 加起來 ≤ 父單位的 `share`**，剩下的算父單位自己（母公司本身） |
| `staff` | 員工數，只用來算「這個單位是大是小」；不用個別建立人 |
| `stocks` | 對應的館外股票 id（可以有多支）；沒有就 `[]`。集團的 h 看旗下股票的平均（見 4.1） |
| `story` | `true` 的單位是劇情單位（2.4），數字不照一般公式算 |

**算帳規則**：只有「葉子」（沒有子單位的）和「集團自己的那一份」有 `cash`。集團的總現金＝自己的＋所有子孫的加總。**薪水、預算先在集團層級算總額，再分給底下的人**；之後細分到公司，只是把集團那份往下拆，總額不變。

### 2.3 名單和檢查工具

- 名單放 `content/world/units/<id>.json`，一個單位一份（像 `content/npc`）。
- `tools/world_check.cjs`（`npm test` 會跑）檢查：
  - id 不重複、`parent` 指得到、沒有繞圈；
  - **兩層加總對得上**：子單位 `share` 的總和 ≤ 父單位；全部頂層 `share` 的總和 ≤ 90%（剩下是公共池）；
  - `stocks` 都存在於 `OUT_STOCKS`，而且**每支館外股票只掛在一個單位下**；
  - 每位 NPC 的 `job.unit` 存在；沒有單位的人有 `job.kind`（student、retired、free）；
  - 每個集團至少有一位 NPC（不然是死單位；`g-public` 第一版例外）；
  - 劇情單位（`story: true`）的欄位白名單（見 2.4）。

### 2.4 文化部：獨立的劇情單位

翊文：「文化部獨立出來，在這個世界裡是有種神秘可以接在劇情裡主要的存在」。

- `u-culture` 的 `kind` 是 `story`，`parent` 是 `null`，不掛任何集團。
- **經濟上刻意不完全公開**：財報只寫看得到的兩件（補助新玩家、館債，決定 0082），不列它的規模、營收、員工。這些欄位在名單裡標「**劇情決定的欄位**」，**第一版不寫死數字**：`share`、`staff` 先用最小值（`share` 0.02）讓守恆算得下去，不當成一般公司；要改規模要先問 Yuga 劇情怎麼走。
- 它的 `cash` 照舊從外面世界出（`cultureStart`、館債債主），守恆照一般單位算；**h（健康值）不用公式算**，固定當 1.0（不隨景氣減薪、不裁員、不吃緊停止補助），因為它的行為由劇情決定（見 8 的第 7 題）。
- 檢查工具對劇情單位只檢查「id、`parent`、`share` 在範圍內」，不檢查「有沒有 NPC」。**不要把它的劇情資訊（為什麼補助、錢哪來）寫進名單或程式碼註解**，這些在 `content/story/帳本.json`，收尾由翊文決定（`docs/未來更新.md` 三）。
- 館外股票那些公司的「組織」與劇情無關，不受這一點影響。

## 3. NPC 的隸屬和薪水

### 3.1 欄位（`content/npc/<id>.json` 加 `job`）

```json
"job": { "unit": "g-daily", "title": "司機", "level": 2 }
```

沒有單位的：`"job": { "kind": "student" }`（student、retired、free）。`tools/npc_check.cjs` 跟著檢查。

### 3.2 薪水是多少

現在每位 NPC 有 `budget.perDay`（47 位有預算，加起來每天 2,894 萬）。**這是「今天最多可以花多少」，不是真的花的錢**（真的每天約 13 萬）。所以薪水不要直接等於 perDay：

- 不要把薪水定成「perDay 除以某個比例」：那會得到每天上千萬的薪水，比池子每天的成長還大。
- 薪水**維持 perDay 的量級不變**，改叫「生活預算」，由單位按「薪水倍率」調：
  `今天的預算 ＝ perDay × 倍率（單位的健康值決定，見 4）`
- 這樣第一階段**不用重算任何 NPC 的數字**，只是多一個倍率；現在的上限（每人每天 `dayPct`、全館每天 `dayCap`、外面世界 20%）全部照舊。

### 3.3 錢從哪裡出（兩階段）

**階段 A（建議先做）：薪水只是預算，錢從單位出。**

- NPC 來館花的錢，從所屬單位的 `cash` 出（不是公共池）。帳上來源仍寫 `npcFood`、`npcTicketBudget`…（日報、`econ:check` 不用改），多記一個 `by 單位`。
- 單位的 `cash` 由每天分到的成長補（1.3）。單位 `cash` 不夠就當天不花（吃緊，跟現在的 `casWorldLow` 一樣有下限）。
- **守恆**：公共池 ＋ Σ單位 `cash` ＝ 現在的池子。每天只有 `worldGrow` 是憑空；NPC 花錢是單位 → 館（搬）。
- 沒有單位的人（學生、退休）：從「家計」出。家計是一個虛擬單位 `u-household`，`share` 約 10%。

**階段 B（之後）：NPC 有自己的錢包。**

- 每天發薪：單位 → NPC 錢包（搬）；NPC 花在館內是 NPC → 館；剩下的留著（儲蓄），可以買畫、買館內股、去賭場（NPC 步驟 5 以後）。
- NPC 不會憑空多錢：NPC 在館外的消費（沒進館的部分）「搬回」公共池，不然錢會一直累積在 NPC 身上。
- 要做階段 B 要先有 NPC 的資料文件（5.3）和每日發薪排程。**不建議在第一輪就做。**

### 3.4 為什麼 A 先做

- A 不改任何 NPC 的行為，只是帳從「公共池」改成「單位」。壞了容易退。
- B 會讓 NPC 的錢變成要追蹤的東西（NPC 之間、NPC 跟玩家都有買賣，容易長出「穩賺」，`docs/經濟系統的坑.md` 第四節）。

## 4. 跟現有東西連動

### 4.1 單位的健康值 h

每個單位每天算一個健康值 `h`（集團的 h ＝ 旗下股票的週漲跌平均＋景氣；有子公司之後，母公司的 h ＝ 自己和子公司 `share` 加權平均；**文化部固定 1.0**，見 2.4），範圍 0.6～1.2，**不是即時的**（防止時間差，經濟系統的坑第三節）：

```text
h_i（今天） ＝ clamp( 1 ＋ 景氣b × 行業係數_i ＋ 股價週漲跌_i × 0.5 , 0.6 , 1.2 )
```

- 景氣 `b`：現有的（館內景氣＋外部景氣，`casGdpExt`）。
- 股價週漲跌：只有上市公司有（館外股票的 7 天漲跌，真實行情，**用昨天以前的收盤**，不是現在價，玩家不能靠今天的盤中賺到「公司好壞」）。
- 公家機構和其他單位：只看景氣。

### 4.2 薪水倍率、減薪、裁員

| 狀態 | 條件 | NPC 預算倍率 |
| --- | --- | --- |
| 一般 | h ≥ 0.9 | ×1.0（h ＞ 1 時最多 ×1.1） |
| 減薪 | 0.75 ≤ h ＜ 0.9 | ×0.8 |
| 緊縮 | h ＜ 0.75，連續 2 週 | ×0.5，這個單位的 NPC 一半「休假」（今天不來） |
| 裁員 | 緊縮連續 4 週 | 個別 NPC `laidOff`，預算降到 ×0.3（不是 0），來館次數減半，**之後 4 週內有機率找到新工作**（見 7 的選項） |

- **下限**：任何 NPC 的預算不會低於 perDay × 0.3；全館 NPC 來館人數不會低於現在的 50%。（館內人流一夜消失會讓館內股變「人太少」、財報變空。）
- **每週結算一次**，不是每天；減薪和裁員的消息放在日報和市場新聞，不隨機突然發生。
- 景氣差時全館 NPC 預算變少、來館少，會讓館的收入變少：這是設計想要的「世界經濟影響館」，但要用模擬驗證不會讓莊家破產（`test/sim_econ_world.cjs`）。

### 4.3 新聞、日報、財報

- **市場新聞**（每日排程的 market）：多一類單位消息（「島線電話行景氣轉好，薪水調升」「某某機構縮編」），由 h 的變化機械產生，不用人寫；重要的單位事件（劇情相關）仍由人寫。
- **日報**：多一行外面世界（「台灣景氣 … 外面世界今天成長 … 萬；N 家單位減薪、N 家緊縮」）。
- **財報**：銀行財報頁加「外面世界」卡片（由美術統籌排版，資料來自 `h.econ.ext` 的同一套）：池子、各單位 h 的分布、NPC 來館花費（已經有）。

### 4.4 跟現有守恆檢查接

新增 `econ:check` 一項：**公共池 ＋ Σ單位 cash ＋ Σ NPC 錢包（階段 B）的每天變化 ＝ 當天的 `worldGrow` − 館內帶走的 ＋ 館內帶進來的**。`econ:check --ledger` 讀正式站帳面時也要有這一項。

## 5. 資料怎麼存

### 5.1 現在

`casinoHouse/main` 一份文件裝所有東西：莊家、預算池、外面世界、館債、NPC 進度、股票、投資…… 現在約 30 KB（Firestore 單份上限 1 MiB，用了 3%），但**每次賭場動作整份讀寫**（交易讀 house＋wallet，寫兩份），而且文件越大越慢、越容易兩個動作互相卡住。

### 5.2 建議（翊文 11-15 同意的方向）

| 文件 | 內容 | 誰碰 |
| --- | --- | --- |
| `world/main` | 公共池、規模、成長紀錄、GDP 資料的引用 | 每天排程 |
| `world/units/{id}` | 單位的 `cash`、`h`、狀態、最近的流水 | 每天排程；NPC 來館那一刻（階段 A） |
| `world/npcs/{id}`（階段 B） | NPC 的錢包、`laidOff`、換工作紀錄 | 每天排程 |
| `worldDays/{日期}`（Firestore 路徑要偶數段，所以不是 world/days/{日期}） | 當天一份紀錄：成長、各單位分到多少、h、新聞 | 每天排程寫一次 |
| `casinoHouse/main` | 只留「館」的帳：莊家、預算池、館債、投資、股票 | 館友動作 |

- 館與外面世界的來往（`casWorldOut/In`）仍記在 `house.world`，**當成館的「對外帳戶」**；每天排程把這個帳戶跟 `world/main` 結算一次（搬）。這樣館友動作不用多讀外面世界的文件。
- 守恆：結算前後，`house.world` ＋ `world/main` ＋ Σ單位 `cash` 的總和不變（除了 `worldGrow`）。

### 5.3 排程

- Cloud Scheduler 免費只有 3 個，現在都用掉了（`auctionTick`、台股、美股）。**併進每小時的 `auctionTick`，只在 05:05 那次多跑「換日」**：發成長給單位、算 h、每週一結算減薪／裁員、寫 `world/days/{日期}`。
- 要冪等：用「日期」當 key，同一天跑兩次只算一次（跟 `casInRoll` 一樣）。
- 失敗要補：隔了幾天沒跑，一天一天補（最多 30 天），跟 `casHouseFix` 的補日一樣。

### 5.4 要量的

- `house-size` 固定動作（`tools/fb_task.cjs`）已經量得到 `casinoHouse/main` 的大小；新增 `world-size`（只讀），量 `world/*` 的文件數和大小。
- 預期：每天寫 `world/days` 一份（約 5～10 KB）、單位 25 份、NPC 54 份；每天讀寫 ≤ 100 份，**遠低於免費額度**。

## 7. 更新用的腳本

翊文：「要用快速準確的腳本來更新這些東西」。每一種要定期更新的資料，都配一支 `tools/` 腳本（`npm run` 指令）；腳本會**檢查格式、守恆、兩層加總**再寫檔，**排程和 AI 都不手改 JSON**。`content/排程說明.md` 之後改成叫這些腳本。

| 資料 | 指令（建議名） | 誰用 | 做什麼 | 會擋哪些錯 |
| --- | --- | --- | --- | --- |
| 台灣總體經濟（GDP 年增率、名目 GDP、近四季） | `npm run world:gdp -- --quarter 2026Q4 --yoy 13.1 --nominal-year 26000000000000 --published 2026-11-27 [--kind 初步統計]` | 每日排程（有新公布時） | 讀 `content/economy.json`，更新 `quarter`、`yoy`、`history`（自動推最近四季、最後一個等於 `yoy`）、名目 GDP；加 `--dry` 只印差異 | 年增率不在 −30～40、`history` 長度不對、日期比現有的舊（不能倒退）、沒有 `published`；名目 GDP 一次變動超過 ±10% 要加 `--force` |
| 單位名單（加、改、掛） | `npm run world:unit -- add g-new --name … --sector … --share … [--parent g-island]`、`-- set g-island.share 0.1`、`-- move c-x --parent g-y`、`-- list [--tree]` | AI、翊文 | 每次寫一份 `content/world/units/*.json`，寫完自動跑 `world_check`；`--tree` 印成縮排的樹 | 繞圈、`share` 超過父單位、股票重複掛、id 不存在 |
| NPC 的隸屬和薪水 | `npm run world:npc -- assign c-bus --unit g-daily --title 司機 [--level 2]`、`-- list --unit g-daily`、`-- orphans`（列沒有隸屬的人） | AI、翊文 | 改 `content/npc/<id>.json` 的 `job`，不動其他欄位；`orphans` 一眼看到哪些人還沒掛 | 單位不存在、劇情角色（t-）掛到會破梗的單位、沒有單位又沒有 `job.kind` |
| 預算和薪水總額 | `npm run world:budget -- [--unit g-daily]` | AI、翊文 | 印每個集團：NPC 人數、`perDay` 加總、倍率後的預算、占全館每天上限的比例 | 預算加總超過全館每天上限（`dayCap`）、超過集團的現金能付的天數 |
| 改數字前的預覽 | `npm run world:sim -- --days 30 [--b -0.5] [--set growBase=…]` | AI、翊文 | 跑 30 天（`sim_econ_world`、`sim_npc_casino` 的組合）：各池子、單位現金、NPC 預算、來館人數、莊家會不會破產 | 莊家或預算池破產、NPC 來館低於 50%、守恆差不是 0 |
| 世界市場新聞 | `npm run world:news -- add --date 2026-11-17 --title … --text …`（寫進 `dN.json` 的 `market`） | 每日排程 | 檢查字數（標題 14 字內、內文 60 字內）、不寫真實企業或國家名、不預告漲跌 | 超過字數、有真實名字、日期不對 |
| 正式站現況（要翊文同意） | 接現有 `npm run econ:status`、`house-size`，之後加 `world-size` | 翊文同意才按 | 下載帳面，交給 `econ_check --ledger` 檢查 | 帳不平（守恆差）、文件太大 |

- **共同規矩**：都有 `--dry`（只印不寫）；寫檔照原本格式（JSON、縮排 2），`git diff` 只看到改的那段（像 `npm run ledger` 那樣）；失敗時 exit 1 並說明哪一項沒過。
- **誰先做**：`world:gdp`（最常用，排程每天都會碰到）和 `world:unit`＋`world_check`（W1 一起做）；`world:sim` 在 W4、W5 前做；其他跟著各步。
- **不碰正式站**：這些腳本只改 repo 裡的檔案；真的寫進正式站的，只有排程和伺服器自己（`auctionTick` 那次換日）。

## 8. 要翊文定的事

每項都附建議。標「必選」的要先定才能開始。（更新用的腳本是第 7 節，不用另外選。）

1. **（必選）第一版的集團要哪幾個？** 建議 7 個集團／組織（島上科技、海外科技、民生、金融、文化藝術、學校研究、公共機構）加獨立的文化部，名字和分法見 2.1，**名字是草稿，Yuga 可以改**。公司、子公司第一版先不開（資料結構已經留好 `parent`）；要不要先把館外股票那 11 家各開成一間公司掛在科技集團底下，建議 W5 之後再說。
2. **（必選）要不要採「階段 A 先、階段 B 之後」？** 建議是。階段 A 只換帳，不改 NPC 行為；階段 B（NPC 有錢包）等 W5 穩定幾週再說。
3. **（必選）φ 和成長速度**：用現在的池子反推 φ＝0.04%（餘額不動）？每天成長用近四季平均 13.9%（建議）還是最新一季 14.36%？（延續幣值規劃 8.7 的第 1、2 題，兩題只要答一次。）
4. **NPC 要不要會換工作？** 建議 W6 才做：被裁員的 NPC 之後有機率到別的單位，日報寫一句。不做的話，被裁員就是長期降預算。
5. **裁員要不要？** 建議要有，但很慢（緊縮連續 4 週才裁）、有下限（預算 ×0.3、全館來館人數 ≥ 50%）。不要的話，最差只到「緊縮」（×0.5）。
6. **玩家能不能跟單位互動？** 選項：
   - 不能（建議，第一輪）：單位只是背景，NPC 預算和新聞有連動；
   - 能投資：買單位的股（已經有館外股票，館內再加「機構債」之類）；
   - 能打工：到單位上班領薪水（要小心刷錢，會動到經濟系統的坑第四、五節）。
7. **文化部的規模和補助怎麼處理？** 它是劇情單位（2.4）：第一版 h 固定 1.0、不減薪不裁員、規模欄位不寫死、財報只寫補助新玩家和館債。現在補助新玩家不設上限（決定 0082），人多時外面世界的池子會降；要不要「補助隨池子降到吃緊線時變少」（建議，自然），或是讓劇情決定，翊文和 Yuga 定。
8. **單位好壞要不要讓玩家看得到？** 建議財報有「外面世界」卡片（各單位 h 的分布，不列每家的數字，免得洩漏股價方向）；市場新聞只寫「某某減薪」這類已發生的事，不預告。
9. **哪些集團、公司會牽涉劇情？** 文化部已經是；其他集團（例如金融集團接 Yuga Bot 銀行的劇情、文化藝術機構接畫和拍賣）要不要也有「神秘」的一面，要先由翊文和 Yuga 決定。名單裡只放「明面」的欄位，劇情的部分標「劇情決定的欄位」，我不自己定。

## 9. 風險和還沒查的

- **玩家用單位消息賺錢**：單位 h 是每天算一次、用昨天以前的收盤、新聞只報已發生的事，所以沒有時間差；仍要用模擬看「看了新聞買股票」有沒有穩賺（`docs/經濟系統的坑.md` 第二、三節）。
- **台灣 GDP 的真實數字**：我寫的「約 25 兆」是記憶裡的量級，W2 之前排程要去主計總處查實再填。
- **NPC 預算變少的後果**：館的收入變少，要看莊家、預算池撐不撐得住（`sim_econ_world.cjs`）。W5 才做，要先跑模擬再上線。
- **資料拆文件**：交易的一致性（館友動作寫 house＋wallet，排程寫 world）靠「對外帳戶」切開，兩邊不要同時改同一份；要寫測試模擬同時發生。
- 劇情不能破梗：單位和 NPC 的 `job` 欄位只放明面的；不要把劇情組織放進來，除非 Yuga 同意。
