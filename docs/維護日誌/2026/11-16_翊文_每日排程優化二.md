## 為什麼要改

> 「day:new 也產生週一的 week.json 骨架」「拆開最慢的經濟檢查測試：只改內容的 PR 在 CI 不跑那一項，部署前的最後一道一定跑全套」「排程說明的時間：每天 08:23（台灣）跑，維持不改，順便檢查館訊會不會在內容上線前就發舊的」（翊文 11-16，接 PR 623 的每日排程優化）

## 改了什麼

- **週一的 week.json 骨架**（`tools/day_new.cjs`）：週一、這週的 `week.json` 還沒有時，`npm run day:new` 先建它：title、theme、question、summary、lines（這週的線寫「待寫」、帳本 `main.seasons` 有這週就放主線 `main-sN`〔名字照上週〕、季節線 kind season）、5 個 weekly 空殼、weeklyBonus、ending。新一季頭一週 summary 第壹行自動寫「📖 主線第 N 季〈季名〉開始：第壹章〈章名〉」。`answer` 週日才寫，骨架不放；印出 `unit`／`unitRole` 和選填欄位的提醒。已經有檔不覆蓋。`day:check --strict` 現在連 `week.json` 的「待寫」也擋（`answer` 不算）。
- **只改內容的 CI 跳過最慢那項**：內容路徑的判斷從 `tools/ship.cjs` 抽到共用的 `tools/changed_files.cjs`（ship 和 CI 同壹個），它用 `git diff` 跟 base 比對，只改內容的 PR 把 `SKIP_SLOW_ECON=1` 寫進 `$GITHUB_ENV`；`test/run_all.cjs` 看到就跳過「經濟自我檢查腳本」（約 114 秒）並印壹行「只改內容，跳過經濟自我檢查」。`ci.yml` 接上；**`deploy.yml` 不接**（部署前的最後一道壹定全套，加註解），有程式檔、不是 pull_request、讀不到差異都全跑。`test/ci_skip.test.cjs` 驗這些。
- **排程時間**：`content/排程說明.md` 開頭、第〇節、第三節改成「每天 08:23（台灣）跑」，說明 05:00 換日、08:23 以前今天的書還沒上是設計好的。
- **館訊和排程的時間**（`tools/announce.cjs`、`discord-scheduled.yml`）：今天的 `dN.json` 要等排程合併進 main 才存在，所以不會先發舊的；但合併之後、部署完之前跑到定時備援，會在內容還沒上線就發。定時備援從 08:27／08:47 改到 09:17／09:37（排程 08:23 開始、約 08:55 部署完之後），而且「定時」那幾次要等最新一次部署成功（讀部署狀態時加比對 commit，還沒開始跑的算「未上線」）才發今日館訊；手動叫的（ship 部署成功後、deploy.yml 最後壹步）仍只擋壞掉的部署，不然 deploy.yml 自己叫的時候它還在跑，永遠發不出去。
